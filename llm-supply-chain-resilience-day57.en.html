Day 57 Hard LLM Infra Reliability Vendor Risk 2026-10-07

LLM Supply-Chain ResilienceWhen Your Core Dependency Can Cut You Off, Reprice, or Compete

Scenario + Requirements

You own an AI coding assistant: 2M DAU, about 40M model calls per day, peaking around 2,000 RPS, with 75% of traffic on a single closed frontier-model vendor. Traditional dependencies (databases, clouds) fail by going down. This one has three extra failure modes: cutoff, repricing, and competing with you. All three have already happened:

  • Cutoff: in June 2025 Windsurf disclosed that Anthropic was revoking almost all of its first-party Claude 3.x capacity with less than five days' notice, against the backdrop of reports that OpenAI was acquiring Windsurf. In August 2026, after SpaceX acquired Cursor, OpenAI announced it would stop supplying models to Cursor (Cursor said OpenAI models served about 5% of its traffic).
  • Repricing / rule changes: GitHub said Copilot's premium request model was "no longer sustainable" and moved all plans to token-based usage billing from June 1, 2026. From April 2026 Anthropic stopped letting subscription limits cover third-party harnesses such as OpenClaw, then paused a broader billing change — the rules themselves changed repeatedly within one quarter.
  • Competing: vendors ship their own applications (Claude Code, Codex, and so on). You are both a large customer and a competitor.

Requirements: if any single vendor cuts you off completely within 72 hours, core features stay up and quality regression is measurable and bounded; each task has a hard cost budget and gross margin stays non-negative; p95 time-to-first-token (TTFT) stays under 1.5s through a switchover.

Core insight: this is not an availability problem you fix by "adding a fallback". It is supply-chain management. Vendors have their own strategic intent, and the failure modes are correlated, announced with short notice, and commercially motivated — nothing like random hardware faults.

The Gateway translates product requests into one internal schema (messages, tool definitions, cache hints); product code never imports a vendor SDK directly. The Router picks a model by asking: what capability tier does this task need, how much budget is left, and who is healthy right now. Adapters absorb vendor differences (tool-call formats, prompt-caching semantics, streaming events). The eval harness keeps scoring every candidate on shadow traffic and produces a capability matrix for the Router — without it, every switch is a blind switch. The contract registry turns commercial terms into data the router can read.

Key Point 1: Model Abstraction Layer and Capability Contracts

One-line trade-off: the thicker the abstraction, the faster you can switch — but it flattens each vendor's unique features (caching, long context, specific tool formats). You pay a performance tax for portability.

Principle

The goal is not "all models are the same" but making differences explicit. Each model declares a capability contract: context length, parallel tool calls, strict structured output, prompt-cache granularity and TTL, price. Each request declares what it needs. Routing is constraint matching, not swapping a model-name string. The most dangerous anti-pattern is the half abstraction: the interface is unified, but the prompts were tuned against one vendor — on switchover nothing errors, and quality quietly drops. So prompts are versioned per model family and stored alongside the adapters.

Trade-offs

OptionYou gainYou give up
Direct vendor SDKNew features on day one, lowest latencySwitching cost measured in lines of code; a cutoff means editing product code
Lowest-common-denominator APISwitching is a config changeDifferentiators like prompt caching and extended thinking go unused; you lose on both cost and quality
Capability contract + opt-in extensions (recommended)Portable by default; unique features used explicitly with the dependency registeredYou maintain a capability matrix and per-vendor prompt variants; eval cost grows linearly with model count

Pseudo-code

# Capability contract: requests declare needs, the router matches constraints (pseudo-code)
@dataclass
class Capability:
    max_context: int
    parallel_tools: bool
    strict_json: bool
    cache_ttl_s: int          # 0 = no prompt caching
    usd_per_mtok_in: float
    usd_per_mtok_out: float

def eligible(req, models):
    out = []
    for m in models:
        cap = m.capability
        if req.tokens_est > cap.max_context: continue
        if req.needs_parallel_tools and not cap.parallel_tools: continue
        if req.needs_strict_json and not cap.strict_json: continue
        if m.quality[req.task_type] < req.min_quality: continue  # from the eval matrix
        out.append(m)
    return out

def render_prompt(req, model):
    return PROMPTS[req.task_type][model.family].format(**req.vars)  # prompts versioned per model family
Real-world case: when Windsurf lost its first-party Claude 3.x capacity in June 2025, it had less than five days to find other inference providers. The value of an abstraction layer has to be paid for before the cutoff — writing adapters in the middle of one is too late. In the industry, OpenRouter's provider routing turns multi-host routing and multi-model fallback into request parameters (a prioritized models list, allow_fallbacks, sorting by price / throughput / latency) — "abstraction layer as a service", at the price of one more third-party dependency.

Key Point 2: Multi-Vendor Routing — Warm Standby, Not Cold

One-line trade-off: running real traffic on several vendors (active-active) is expensive and inconsistent; switching only when something breaks (active-passive) is cheap, but the standby path silently rots.

Principle

Day 23 covered circuit breakers, retries, and bulkheads; the new problem here is keeping the standby path fresh. A fallback that never carries traffic has stale prompts, quotas, accounts, and rate limits — on cutoff day you discover the standby account's rate limit is 1/20 of the primary's. So the standby vendor should permanently carry 5–15% of real traffic, with capacity confirmed in writing. The second problem is correlated failure: a cutoff rarely looks like a 5xx. It looks like 403s, a sudden quota drop, or a model version being retired, and health checks must treat those as failures too. Third, degrade by capability tier: when the primary is gone, completion tasks can drop to a small open-weight model, but complex agent tasks should queue rather than fall to a model that will mangle code.

Trade-offs

OptionYou gainYou give up
Single vendor + cold standbySimplest; one set of prompt tuningStandby path unproven; no capacity guarantee; quality unknown on switch day
Primary + warm standby (10% resident)Standby continuously validated by real traffic; capacity and quota provenTwo prompt sets and two eval tracks; slight UX inconsistency
Vendor per task typeBest price-performance per task; naturally diversifiedAny one cutoff takes out a whole feature class; most complex routing policy

Pseudo-code

# Routing with breakers and tier-aware degradation (pseudo-code)
FATAL = {401, 403, 404}          # auth failure / model retired: not jitter, a cutoff signal

def route(req):
    for m in rank(eligible(req, MODELS), by=req.objective):   # cost or latency
        if breaker[m].open(): continue
        try:
            resp = m.adapter.call(req, timeout=req.ttft_budget)
            breaker[m].success()
            ledger.charge(req.task_id, m.cost(resp.usage))
            return resp
        except ProviderError as e:
            if e.status in FATAL:
                breaker[m].trip(hold_s=3600); alert("supplier-level", m, e)
            else:
                breaker[m].failure()
    if req.tier == "agent":
        return enqueue(req)        # queue rather than drop to an under-capable model
    return degrade(req)            # completion tasks: fall to a small open-weight model
Real-world case: in August 2026 OpenAI announced it would stop supplying SpaceX-owned Cursor, with access ending in mid-November. Cursor said OpenAI models served only about 5% of its traffic — a diversified traffic mix turned a cutoff into a controlled migration — and Anthropic publicly said it would keep adding compute for Claude in Cursor. Compared with Windsurf in 2025, the difference was not technology; it was how diversified traffic already was before the cutoff.

Key Point 3: Open-Weight Floor + Per-Task Cost Budgets

One-line trade-off: open weights give you sovereignty and a cost floor, but you own post-training, inference ops, and the capability gap; budgeting by per-token list price systematically underestimates what reasoning models really cost.

Principle

Gundlach et al. at MIT FutureTech (2025) estimate that the price of reaching a fixed benchmark level falls about 5–10× per year, while the price of running frontier models themselves rises about 3–18× per year — bigger models and more reasoning tokens. The price sheet gets cheaper while your actual bill may grow: on the same task a reasoning model can emit an order of magnitude more tokens. So the budget unit must move from "dollars per million tokens" to "dollars per completed task", charged in real time per task, downgrading or stopping when over budget. Open weights are the floor of that ledger: their price cannot be raised unilaterally, and they cannot be taken back when you get acquired.

Trade-offs

OptionYou gainYou give up
Closed frontier onlyStrongest capability, zero opsPrice and supply decided by the other side; margins capped by upstream
Hosted open weights (third-party inference)No GPU ops; switching host means switching an endpointStill a host dependency, but you can move between hosts
Self-run open weights + own post-trainingCost and roadmap under your control; RL on your own tasksGPU capacity planning, inference optimization, a training team; the capability gap is closed by post-training

Pseudo-code

# Per-task budget ledger: bill per completed task, not per token (pseudo-code)
class TaskBudget:
    def __init__(self, task_id, usd_cap, tier_ladder):
        self.spent, self.cap, self.ladder = 0.0, usd_cap, tier_ladder

    def before_step(self, est_tokens, model):
        projected = self.spent + model.cost_estimate(est_tokens)
        if projected <= self.cap:
            return model
        cheaper = self.ladder.next_below(model)       # step down: frontier → workhorse → open weights
        if cheaper and self.spent + cheaper.cost_estimate(est_tokens) <= self.cap:
            return cheaper
        raise BudgetExceeded(self.task_id, self.spent)  # product layer: tell the user or hand off

    def after_step(self, usage, model):
        self.spent += model.cost(usage)   # reasoning tokens count too: the part the price sheet hides
        metrics.histogram("usd_per_task", self.spent, tags={"model": model.name})
Real-world case: in March 2026 Cursor acknowledged that Composer 2 is built on Moonshot's open-weight Kimi K2.5 plus extensive RL post-training, used under a commercial arrangement through Fireworks AI. According to TechCrunch's April 2026 reporting, its in-house Composer plus calling cheaper models such as Kimi helped its enterprise business reach slightly positive gross margins (individual developer accounts still lose money). GitHub Copilot moving to token-based billing is the other end: the reseller hands the cost risk back to the user.

Key Point 4: Contracts, Capacity Terms, and an Eval Gate Before Switching

One-line trade-off: long contracts and reserved capacity buy price and supply certainty but deepen lock-in; short contracts stay flexible but give you nothing in writing when a cutoff comes.

Principle

Technical redundancy only shortens recovery after a cutoff; contract terms decide how much warning you get. Terms to negotiate: termination notice period (Windsurf had under five days), change-of-control clause (can the vendor terminate unilaterally when you are acquired? — in the Cursor case OpenAI's stated reason was distrust that the new parent would honor its terms), model deprecation notice, reserved capacity and rate quotas, price-lock period, and data-use restrictions. The other half is an eval gate: before moving to a new model, compare task pass rates on a golden set plus shadow traffic. The regression must be measurable and bounded; otherwise the switch just ships a quality incident to users.

Pseudo-code

# Switch gate: each task type's quality drop must stay within bounds (pseudo-code)
def promote(candidate, incumbent, task_types, max_drop=0.03):
    plan = {}
    for t in task_types:
        base = eval_pass_rate(incumbent, GOLDEN[t]) if incumbent.alive else BASELINE[t]
        cand = eval_pass_rate(candidate, GOLDEN[t])
        shadow = shadow_agreement(candidate, t, sample=0.02)   # online shadow comparison
        if base - cand <= max_drop and shadow >= 0.9:
            plan[t] = "ramp"          # 10% → 50% → 100%
        else:
            plan[t] = "hold"          # stay on standby / queue / tell users capability is limited
    return plan
Real-world case: from April 4, 2026 Anthropic stopped letting subscription limits cover third-party harnesses such as OpenClaw (with a one-time credit as compensation); a broader billing change planned afterwards was then paused on June 15, 2026, the day it was due to take effect. For downstream builders the lesson is not which rule was right but that usage rights not backed by a contract can change at any time: a tool built on consumer subscription limits has no notice period at all.

Scaling and Optimization

  • From multi-model to multi-host: deploy the same open-weight model on two inference providers plus one self-run cluster. What fails is a host, not the model, and prompts need no retuning.
  • Cost observability: break down usd_per_task P50/P99 by task type, user tier, and model; watch for long-tail tasks (agent loops) eating most of the budget — Day 53's fat-tail thinking projected onto the bill.
  • Regular cutoff drills: as with Day 44's chaos engineering, once a quarter force the primary vendor's traffic to zero for an hour off-peak to validate standby capacity and the eval gate.

Common Pitfalls + Interview Questions

  • Pitfall: treating a cutoff as an availability problem. Only retries and 5xx breakers; real cutoffs show up as 403s, quota drops, and retired model versions, and they don't self-heal. Follow-up: "How does your breaker tell jitter from a cutoff?"
  • Pitfall: a cold standby that never carries traffic. On switch day you find the standby quota is too small and the prompts were never tuned.
  • Pitfall: costing by per-token list price. Reasoning models can use an order of magnitude more tokens; budget per completed task.
  • Pitfall: unifying the interface but not the evals. The switch throws no errors while quality silently drops — exactly Day 54's "fails fluently" failure mode.
  • Interview question: "Your primary vendor gives you 72 hours' notice. What do you do in the first 24?" A strong answer covers, in order: freeze traffic share, confirm standby capacity, run the eval gate, ramp by task type, and tell users what capability changes.

Reflections

How much does carrying 10% of traffic on a warm standby cost? Argue with an order-of-magnitude estimate whether it is worth it.

Say monthly model spend is $1M and the standby is 20% pricier per unit: 10% of traffic costs about $20K/month extra, plus a second prompt-and-eval track (about half an engineer). Compare: if a cutoff stops core features for 3 days at $3M monthly revenue, the direct loss is about $300K before churn. If the annual probability of a cutoff exceeds roughly 10%, the standby pays for itself — and the past 18 months already contain several public cutoffs and rule changes. Frame it as an insurance premium, not redundant waste.

Will multi-vendor routing give users a "split personality"? How do you keep quality differences from feeling like bugs?

Yes. Switching models mid-session breaks style, tool-use habits, even the model's grasp of the codebase. Design principles: session stickiness (no model change within a session unless a breaker trips), route by task type rather than randomly (so differences fall on explainable boundaries), and tell users explicitly about significant degradation. This mirrors the session guarantees from Day 6: read-your-writes guarantees users see their own writes; here you guarantee that within a session the user faces the same "reasoner".

Suppose you are the model vendor. Which downstream customers are most likely to be cut off, and what does that imply for downstream design?

Reason from the vendor's motives: being acquired, or about to be, by a competitor (Windsurf, Cursor); a product that competes head-on with the vendor's own apps; usage patterns that blow up unit cost (subscription limits drained by high-frequency agents). The implication is to include strategic risk in dependency assessment: thicken the standby during fundraising and M&A talks, reduce single-vendor reliance the more your product overlaps with the vendor's own, and never build the core path on usage rights that are not in a contract.

Open-weight model updates can also break your product. Do open weights really eliminate supply-chain risk?

They turn "taken away" into "no longer updated". The weights are yours and old versions run forever, so there is no cutoff; but upstream may stop releasing, licenses may tighten for new versions, and geopolitics may make a given country's models unacceptable to some customers (enterprise procurement review). So the open-weight floor needs multiple sources too: at least two bases from different origins in the eval matrix, and a post-training pipeline that can move between them. The risk does not vanish; it becomes a slow variable, and you get time to respond.

Compare this with Day 55, "Object Storage as the Source of Truth": both stake correctness on one vendor's semantics. What is the difference?

Day 55 stakes it on a primitive like S3 conditional writes — documented, under an SLA, stable for years, with several object stores already compatible with the same semantics, so the replacement path is clear. An LLM dependency stakes it on capability, not an interface: the interface can be unified, but "this model gets this kind of task right" has no spec to be compatible with; only evals can prove it. So redundancy for the former lives at the protocol layer, and for the latter it must live at the eval layer — the eval matrix is the LLM era's compatibility spec.
